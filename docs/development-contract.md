# 共享开发契约

适用于从同一 Git 历史接续的 Windows 与 Linux 开发。具体操作见 [开发接续手册](development-handoff.md)。本文件随源码共享；机器路径、凭据、照片、工作区和私人交接留在各自机器。

## 开始任务

1. 读取本文件、任务范围和该轮交接记录；检查分支、完整 HEAD、共同基线及工作树。旧 `main`、远端默认分支或同名目录不自动代表正确基线。
2. 沿当前历史建立 `topic/<功能>`，不要从源码 ZIP 重新 `git init`。同一功能同一时间只安排一个主写入端。
3. 未提交或未跟踪内容先保护；不使用强制重置、清理或强推解决分叉。其他分支及归档引用不随功能交接一并传输。
4. 使用当地 Python 3.12 与当地虚拟环境。先检查实际导入位置；不复制另一台机器的 `.venv`。

## 行为与数据边界

- 原片保持原位，“弃置”是审核标记；保护人工主体确认、分组、裁切、星级及工作区恢复。
- 人脸候选与人工确认分开；未知、冲突、失效证据保持待确认。自动候选不能变成人工多参考。
- 技术质量、摄影表现和人工决定独立；技术质量不负责拆组。
- 进入 AI 页面只导航；用户主动启动后才请求服务。凭据和完整图片请求不进入日志、报告或仓库。
- 暂缓的算法、模型和研究保持禁用；工程重构不能间接启用它们。
- 测试、数据集和许可证按各自范围使用。真实照片、付费 API、模型下载、发布按当次任务授权处理。

## 平台分工

| Linux / Dot | 原生 Windows |
| --- | --- |
| 纯逻辑、公开资料、授权样本实验、可移植工具与测试 | Tk 生命周期、DPI、快捷键、文件锁、Junction、程序更新 |
| 生成同提交的检查报告和增量 bundle | 验证同提交、修正 Windows 差异、构建候选 EXE |
| 明确 GUI、宿主或数据不可用项 | 真实 Lightroom、目标机器实际工作流验收 |

快速检查只证明其列出的范围；Linux 通过不等于 Windows 通过，候选包通过不等于独立准确率通过。

## 交接与集成

- 发件端提交范围内改动，运行 `tools/check_dev.py`，在干净分支上生成交接包。报告必须匹配 HEAD 与 Git 树，保留跳过原因。
- 收件端从独立记录取得完整 base/head SHA，验证后仅导入新的 `refs/remotes/handoff/...` 引用；先检查差异，再明确执行 worktree／集成。
- Windows 修正继续同一功能链；下一次云端从修正后的提交开始。源代码、模型、依赖和测试证据版本绑定。
- 分叉可以正常合并，但需处理具体冲突并验证合并树。共同历史能保留改动意图，不保证永远没有冲突。
- 完成修改与相称验证后创建本地 Git 提交。不得夹带其他任务、密钥、照片、运行设置或构建产物。
- 推送、Release 与程序安装是独立动作，按用户当次授权执行。没有自动推送。

## 环境与交付状态

`requirements-dev-checks.txt` 仅固定快速检查使用的 pytest，不是完整生产环境锁。`doctor.py` 报告实际版本与能力；生产依赖、特殊解码 wheel 和 Windows 打包环境的完整锁定另行推进。

交接清单的 `windows_application_acceptance=pending` 和 `installed=false` 不会因快速检查通过而变化。文档／辅助工具变动不触发业务 EXE 重建；生产代码变动按项目规则构建、验证，是否替换依照当次授权。

本机已有的 `AGENTS.md` 与私人项目策略继续适用。本文件不取代用户最新指令，也不把缺少私人文件解释为允许覆盖用户数据。
