## 1. 结论与阅读顺序

项目已有完整的扫描、主体调整、分组、技术复核、摄影表现选片和 Lightroom 导出链路。当前最需要的是把已有能力变成稳定、可测、容易修正的产品，并建立两台机器共享的开发基线。

建议按以下顺序推进：

1. 沿用已验证的共享 Git 接续，继续区分源码、独立候选与现用 build17；候选验收和替换分别处理。
2. 优先完成第 3.4 节的日常流程：程序扫描用户指定的漫展照片，逐张展示判断和依据，用户只指出误判或指定需要检查的人物／区域。无需先逐张填写保留／弃置标签。
3. 用这些真实反馈定位选错人、漏脸、范围错误、依据缺失、技术误判、偏好差异和分组问题；保存改前结果，再修正并比较。
4. 复用现有证据面板完善原因筛选、原生局部查看和反馈记录；接着验收组内比较、已有 AI 摄影选片、人工决定及 Lightroom 导出，让日常选片链路可用。新本地评分与算法实验另按证据安排。
5. 出现可复现的问题后，从相关案例中选少量做专项技术标注与算法对照；独立封存评测用于检验算法，不作为日常扫描的前置条件。
6. 加入独立的本地摄影表现排序，之后再考虑个人偏好、语义检索和成片裁切建议。

本次纠偏：此前较多工作投入登记、盲标和合成演示，解决了评测工具的工程问题，但推迟了摄影师查看真实扫描结果这一主线。工具保留复用；28 张公开诊断样本和 6 张试标不再承担进入产品试用的门槛。用户确认的留弃意见按原来源保留，不改写为独立技术真值。

阅读建议：日常开发先读第 4 节；安排迭代看第 8 节；选择外部项目看第 6 节；实验与验收看第 7 节。

## 3. 产品目标与架构方向

### 3.1 用摄影师完成任务的成本衡量产品

核心目标：在保护原片和人工决定的前提下，让摄影师更快找到可交付照片，能理解建议、修正错误，并稳定进入 Lightroom。

建议长期跟踪五项产品指标：

- 每 1000 张照片的实际人工处理分钟数，分别统计选人、改框、改组、技术复核、选片和导出。
- 必须保留的照片被错误建议弃置的比例，以及模糊照片被自动保留的比例。
- 需要人工处理的照片／组比例，及其中属于数据、主体、算法、API 的原因分布。
- 组内优选命中率与成片多样性：同一表情的重复高分片不能挤掉动作、构图不同的好片。
- 恢复、迁移、重复导入和更新后的结果一致性；人工记录丢失应视为发布阻断项。

所有改善幅度需要基线与对照后再报告。本文没有宣称提升多少准确率或节省多少时间。

### 3.2 将四种判断保持独立

| 维度 | 回答的问题 | 能否覆盖其他维度 |
| --- | --- | --- |
| 主体与身份 | 这是谁，检查谁，区域属于谁 | 匹配分高不能伪造人工确认 |
| 技术可用性 | 必需区域是否有充分清楚／严重模糊证据 | 审美高分不能抵消可靠严重技术问题 |
| 摄影表现 | 表情、动作、构图、遮挡和完整性哪个更好 | 评分失败不能被当成中性合格 |
| 人工最终决定 | 用户最终要留哪张、写几星、如何分组 | 人工决定优先，同时保留技术状态和建议来源 |

建议界面可以同时表达：“人工保留”“技术待确认：左眼像素不足”“本地摄影表现：组内第 2”。人工保留不会自动成为算法准确率的真值；人工身份确认也不会成为审美训练标签。

### 3.3 继续保留桌面产品，逐步分离核心服务

沿现有模块渐进整理为：

```text
桌面界面与快捷键
    → 应用服务：扫描／主体编辑／分组／复核／导出
        → 领域对象：照片、主体、区域、证据、建议、人工决定
            → 适配器：解码、检测／识别、质量模块、AI、文件存储、LR
```

先提取纯计算与状态转换，再移动界面代码。每次只拆一个高频改动的职责，保留既有调用接口与回归。当前没有足够证据支持整套重写为 Web、Electron、Rust 或新的 GUI 框架。

建议统一的证据结构至少包含：来源成员与签名、区域／主体 ID、坐标空间、可见性、必要性、有效像素与支撑情况、指标、状态、原因码、算法／参数／模型版本、耗时。不存在、不可见、未计算、执行失败和证据冲突要分开。

### 3.4 当前优先流程：扫描结果供用户纠错

目标流程：**指定本地照片 → 现有算法扫描 → 每张结果与依据 → 用户只反馈有疑问的项目 → 保存修正前后记录 → 定位问题**。以下是待实施的产品要求，不表示已全部具备。

2026-10-22 源码审查确认需要补齐四处：现用 build17 尚无后续加入的组选片逐图证据面板；现有画框不能同时解释全部实际测量子区；生产页缺少独立的技术误判反馈入口；重扫保存当前本地判断，缺少完整的改前／改后技术记录。另需处理已有“保存框选即重扫并重判自动分组”的联动，不能把新反馈按钮直接接到该行为上。依据：[组选片证据](../src/ai_cull_assistant/group_editor.py)、[结果界面](../src/ai_cull_assistant/ai_review_ui.py)、[框选保存](../src/ai_cull_assistant/app.py)、[会话存储](../src/ai_cull_assistant/session_store.py)、[收据接入边界](measurement-time-receipts.md)。

**输入与扫描。** 用户指定照片目录／已有工作区及本轮范围。已有扫描能复用时先读结果；确需新测量时用明确版本、参数和独立诊断工作区运行现有生产流程，不改原片、现用设置或旧人工决定。扫描不要求质量标签、盲标指南冻结或逐张登记表。软件自动登记文件与运行身份，RAW＋JPEG 配对沿用有依据的现有规则，歧义单列；实际用于测量的成员分别记录。首批可选一组连拍或约 30～50 张，数量仅为减轻首次查看负担，不要求用户逐张审核。

**每张都有结果。** 全部输入都留在列表中，区分“建议保留／建议弃置／待确认”和“未执行／读取失败”。优先展示弃置、主体未定和证据不足；保留片同样可浏览、筛选和抽查，不能隐藏漏检或失败。人工未反馈表示未核查，不等于认可。

| 用户需要知道什么 | 结果页的要求 |
| --- | --- |
| 程序检查了谁 | 在整体照片上区分检测候选、实际选用主体与人工确认；自动选择不得显示为人工确认 |
| 程序看了哪里 | 显示本次实际参与判断的脸核心、眼区及已开启身体部位，带对应来源与坐标；候选脸框、相机 AF 框和检查区域不能混用 |
| 为什么给出这个建议 | 一条简短原因，展开可见部位、证据充分性、已记录指标与实际判定条件；未记录的条件不补猜，不伪造置信百分比或病因式解释 |
| 可以核对哪些细节 | 整体图定位与对应原生局部图联动；标明显示倍率、实际像素、JPEG／RAW 内嵌图／RAW 解码来源。放大显示不增加真实细节 |
| 哪些内容尚未判断 | 未检测到、不可见、像素不足、未开启、未支持、执行失败分别显示；眼带测量不冒充逐眼评分，未测手部不显示“手部清楚” |
| 谁作了留弃决定 | 本地技术建议、有效 AI 复核、摄影偏好与人工最终决定并列保留；人工保留不抹掉原有技术问题 |

已有证据可以直接展示。历史记录缺少实际区域或来源时显示“本次记录不足”；必要时通过新的明确扫描补录，不能使用当前参数反推并冒称当时测量事实。查看页面、缩放和筛选不触发扫描或 API。

**反馈尽量少填。** 用户可以用文件名／列表中的照片 ID 加一句话，例如“这张脸是清楚的”“背景路人不用管”“只需要看主体右眼”“手在动，但我想保留这个动作”。也可以点击主体或框出关注区域。普通无异议照片无需提交意见；反馈原因可选，程序不逼用户填写整套区域技术表单。

反馈要区分三种操作：指出疑似误判只追加问题记录；明确指定检查区域形成待应用的范围修改；明确保留／弃置才写人工最终决定。疑问和框选草稿不自动变成留弃。对“不保留，因为噪声／表情／构图”的反馈保留原意，不编码成失焦或拖影。现有算法未支持的部位作为能力缺口保存，不能用画框假装已完成该部位检测。

**保留对照。** 冻结原建议、原理由、来源、范围及版本，反馈另存且可撤回。改框后先明确受影响照片和操作，再按现有受支持的粒度重测，展示改前／改后差异并使相关旧复核失效。当前最小可靠粒度若是整张照片，就据实写整张重算；每区域重算是后续优化。质量反馈本身不拆组；若复用旧入口会连带自动重分组，接入前应分离该副作用或显示影响并另行执行，保留人工组。

**边界与用途。** 这批照片是用户纠错用的开发案例；可统计建议分布、失败、缺项、反馈类别和处理耗时。看过程序结果后只纠正部分照片，不能据此宣称总体准确率，也不能把无反馈样本算成正确。要比较算法时，再对选定案例进行明确技术复核，并另留未用于调参的评测样本。人工标注工具保留作该专项入口，不自动训练或更新阈值。

本机完成扫描与查看即可，不要求把照片上传聊天、Dot 或 GitHub。仅在用户明确选择共享具体案例时提供对应内容；向 Dot 交接可用合成复现和脱敏结构。现有命令行评估收据不等同生产 GUI／EXE 已完整接入。复核列表和可回放的运行记录是近期目标，完整正式评测另列范围。

## 4. Dot Linux 与本地 Windows 的协作方案

### 4.1 本次接续为什么麻烦

迁移记录确认：云端历史从带 `source/` 前缀的源码快照重新建立，之后再把目录移至仓库根；初始快照已经含业务改动。它与本地没有共同祖先。31 个同名差异、78 个云端独有项和129 个本地独有项只是文件清单，无法直接表达功能意图。

于是接续必须人工分类、追踪依赖、保留本地功能、逐项移植，再做 Windows 验证。Linux／Windows 差异增加了后续验证工作，但“重新建 Git 根历史”是这次源码整合困难的直接原因。

还有三个放大成本的因素：研究与正式功能混在同一交接中；模型随源码反复搬运；两端环境和检查命令不够固定。对应措施是共同历史、短分支、明确研究准入、依赖锁定和机器可读交接。

### 4.2 推荐工作分工

| 工作 | 主执行环境 | 交付要求 |
| --- | --- | --- |
| 方案、公开资料、算法实验、纯逻辑测试 | Dot 的 Linux 环境 | 固定源码提交、样本清单、可重跑命令、原始指标和限制 |
| 跨平台核心代码 | Linux 开发，Linux＋Windows 检查 | 同一 Git 功能分支，不维护两套逻辑 |
| Tk 生命周期、DPI、快捷键、窗口、文件关联 | 原生 Windows | 实际窗口验证，不能只看 Linux 截图 |
| 路径身份、锁文件、Junction、长路径、程序更新 | 原生 Windows，另补 Linux 语义对照 | 对环境差异显式建模，不能统一转小写掩盖问题 |
| EXE 构建、安装包、程序替换 | Windows | 固定来源提交、依赖、程序清单和自检 |
| Lightroom Classic 插件验收 | 装有 Lightroom 的 Windows 本机 | 隔离 Catalog，核对真实导入／导出 |
| 私人照片与本机长期工作区 | 本机 | 云端使用需单独确定范围；公开样本不能代替本人场景验收 |

PyInstaller 官方明确其不是跨平台编译器；Windows 程序应在 Windows 构建。[PyInstaller 官方说明](https://pyinstaller.org/en/stable/index.html)

Dot 可以作为协调入口。官方说明支持连接本机并创建／继续本地 Codex 任务，本机需要在线且 ChatGPT 应用开启。若你的账户入口可用，可让 Dot 把 Windows 专属工作交给本地执行，减少“云端模拟 Windows 后再返工”。这不是文件自动同步，也不证明本次已连接成功；本轮未更改 Dot 设置。[OpenAI Docs：Dots](https://learn.chatgpt.com/docs/dots)

### 4.3 方案 A：共享 Git 仓库，作为日常首选

前提是用户明确允许相应远端写入，且要传输的历史经过隐私与密钥检查。当前已有远端不代表本次允许推送；私有仓库也不能容纳密钥。旧历史曾包含本地维护文档，应核查可传输历史范围，不直接 `push --all` 或把所有引用打包上传。

推荐约定：

- 先确认一个集成基线。build18 尚待用户验收，不能假定旧 main 或远端 main 就是正确起点。
- Windows 与 Linux 都从该提交继续同一历史；云端用 clone／fetch，不在源码 ZIP 目录中重新 `git init`。
- 每个功能使用独立短分支，如 `topic/review-reasons`。同一功能同一时段只有一个主写入方。
- 云端提交代码和必要测试；研究代码保持独立入口，不把样本、输出和未启用模型带进生产包。
- Windows 拉取功能分支到独立 worktree，核对共同祖先，跑与改动相称的测试。
- Windows 修正回到同一功能分支或明确的集成提交；云端开始下一项工作前更新到已集成基线。
- 合并后的实际提交再次完成所需检查，不能拿两个父提交的测试结果代替合并树。
- main 的提升、候选包部署和发布分成独立状态。一次验收一个确定的提交。

在同一提交已通过检查且没有新增改动时，不为“再确认一下”反复跑全量测试。

### 4.4 方案 B：不能用远端时，保留历史的增量 bundle

bundle 只是传输媒介；它不会补回本来不存在的共同祖先。两端首次初始化必须来自同一个经过审查的仓库历史。之后按明确基线传增量，模型未变化时不重新分片搬运。

下面是拟采用的命令模板，尚未在本轮执行。占位 SHA 与分支要替换成该轮已确认值；仓库须干净，交付目录不得放在照片或工作区内。

Linux 云端导出：

```bash
BASE_COMMIT='<本轮共同基线完整SHA>'
TOPIC_BRANCH='topic/review-reasons'
git status --porcelain=v1
git merge-base --is-ancestor "$BASE_COMMIT" "$TOPIC_BRANCH"
# 上一命令必须成功，且该分支全部改动已提交。
git bundle create /approved-transfer/photo-cull-topic.bundle "$BASE_COMMIT..$TOPIC_BRANCH"
git bundle verify /approved-transfer/photo-cull-topic.bundle
git rev-parse "$TOPIC_BRANCH"
git diff --stat "$BASE_COMMIT" "$TOPIC_BRANCH"
```

Windows 接收：

```powershell
$bundlePath = 'C:\approved-transfer\photo-cull-topic.bundle'
$baselineCommit = '<本轮共同基线完整SHA>'
git status --porcelain=v1
git cat-file -e "$baselineCommit^{commit}"
git bundle verify $bundlePath
git fetch $bundlePath refs/heads/topic/review-reasons:refs/remotes/cloud/review-reasons
git merge-base --is-ancestor $baselineCommit refs/remotes/cloud/review-reasons
git diff --stat $baselineCommit refs/remotes/cloud/review-reasons
```

每步失败就处理对应原因。接收先导入独立引用，再审查和合并，不直接覆盖当前检出。接收机没有前置提交时，补传经过审查的历史；不要把增量包强行当完整仓库恢复。右侧须使用命名分支引用创建 bundle。[Git bundle 官方说明](https://git-scm.com/docs/git-bundle)

如果历史因隐私原因暂时不能传输，过渡方案是固定同一源码基线与文件哈希，传该基线上的二进制兼容 diff，由本地审查后形成新提交；明确它是补丁工作流。不要让云端自建的历史冒充本地历史。

- 新增 `tools/doctor.py`：报告 Python、实际模块导入路径、Tk、解码能力、模型、ExifTool、资源路径与可写测试目录，不读取凭据或自动下载资源。

OpenAI 官方支持按平台设置本地环境的 setup 与 actions，可把已经验证的检查／构建脚本接成入口；脚本仍保留在仓库中，便于在普通终端复用。[OpenAI Docs：Local environments](https://learn.chatgpt.com/docs/environments/local-environment)

## 5. 全项目改进清单

本节基于当前代码提出工作项。P0 表示阻止错误交付或丢失决定的基础工作；P1 表示下一阶段产品完善；P2 表示有评测条件后加入；P3 表示长期可选。优先级不代表功能已实现，也不等于授权自动执行。

### 5.1 主体、身份与必需区域：P1

**现状。** 已有自动候选、人工确认、多参考、来源签名和手动范围优先规则。当前眼部质量仍主要按一个眼带区域测量，不能等同左右眼独立评分；眼部可见性也没有完整解决。身体自动区域覆盖躯干及上下臂／腿，并裁掉末端部分，尚无独立手部证据。身体具有范围归属检查，但 `semantic_ownership_verified=False`，还不能证明区域内的肢体像素一定属于该人物。[focus_metrics.py](../src/ai_cull_assistant/focus_metrics.py)、[primary_quality.py](../src/ai_cull_assistant/primary_quality.py)、[body_focus.py](../src/ai_cull_assistant/body_focus.py)

**改法。** 将主体选择、身份匹配与质量 ROI 分开保存。现有 ROI 契约已有 ID 字段，但确认路径仍以框坐标生成部分 ID；改框会改变标识。应扩展为照片内持久主体／区域 ID、脸与身体关联、主体级证据指纹，改框保留标识并更新区域版本；跨照片身份关联另外记录。为旧记录制定迁移规则，不直接替换所有 ID。

左右眼分别记录“可见／遮挡／画外／未知”，必要性由可见性和用户目的决定。没检测到脸只表示检测未确定，不自动走风景合格路径。身体检查先验证范围与人物的关联；跨人、错误肢体框、只有少量有效像素时要求调整。若增加手部检查，先单独完成手部定位、可见性、归属、样本标注和严重程度验证；不能假设现有身体指标已经覆盖手部，也不能用躯干分数平均掉新模块发现的可靠手部严重拖影。

身份侧需要补充相似妆造、同角色不同人、口罩侧脸和背景路人的困难负例。多参考只纳入明确确认的范围；冲突候选应可逐个确认、拒绝或跳过，延续现有快捷键和持久反馈。局部质量不足可以降低“此框适合作为身份参考”的信任，但不能反向判定整张照片应弃置。

**验收。** 单人正脸、侧脸、墨镜、单眼遮挡、多人交叉手臂、背景同位置人物逐项覆盖。主体级指纹完成后，修改一个人的框只失效相关技术测量与复核，其他人的有效证据和人工决定保持。组内摄影表现的实际输入变化时，整组比较可以失效，不能为减少重算沿用过期排名。引入分割模型前先测人工 ROI 与现有几何规则的上限。

### 5.2 技术质量：P1 基础契约，P2 算法竞争

**现状。** 来源支撑、人工范围优先和候选时效性已有修复；整合明确保留现有采样与阈值。组内相对质量检查有同组／区域几何约束，但缺少可靠的同主体身份约束。它目前只会把部分“清楚”结果降为待复核，不直接判弃置，风险程度应按实际行为描述。[relative_focus.py](../src/ai_cull_assistant/relative_focus.py)

**改法。** 在现有基线上统一来源记录：RAW／JPEG 成员、实际解码路径、原始与显示坐标、旋转、裁切、插值、有效支撑、处理参数。保留现有每照片共享解码，将来源／坐标／版本契约扩展到尚未接入的模块；预览不足时按需解码 RAW。RAW 内嵌图是带相机处理的证据，要与 RAW 解码证据区分，不叫“未经处理的 RAW 清晰度”。[shared_decode.py](../src/ai_cull_assistant/shared_decode.py)

将局部细节、模糊分布、噪声、主体背景关系和学习型模型做成可独立运行、可禁用、可版本化的模块。保留原始证据和各自适用条件；规则裁决或经过验证的融合器负责综合，避免把不同量纲直接相加。风景用主体／纹理分布，人物用必要部位，不要求同一算法。

同组比较必须匹配同一主体的对应部位，并检查尺度、姿态与有效像素；不可靠匹配就不生成相对结论。全组都糊时保持技术不合格／待确认，不为了选出第一名而授予“合格”。可选“网页交付／大幅输出”容忍配置要清楚标出用途，原始测量不随配置改写。

**验收。** 基线与候选同时离线运行；明确区分数据不足、主体未定和清晰度冲突。高 ISO、强锐化 JPEG、浅景深、小主体、低纹理、运动局部、全组模糊分别报告。DCT、HiFST、LIQE 均以实验身份进入，第 7 节通过后才讨论启用。

### 5.3 分组：P1 修正能力，P2 性能与特定序列

**现状。** 已有分组策略、拆组／相邻合组、人工组保护，以及本次新增的主体质量证据面板。面板有质量原因不等于已经解释“为什么这两张会分在一组”。[grouping.py](../src/ai_cull_assistant/grouping.py)、[group_editor.py](../src/ai_cull_assistant/group_editor.py)、[group_store.py](../src/ai_cull_assistant/group_store.py)

**改法。** 为分组边界保留简短依据：时间差、相似度、主体关系、策略／阈值版本、人工边界。将“完全重复”“近似连拍”“同场景系列”作为不同关系，避免一个相似阈值承担所有任务。先做分组修改撤销／重做、移到指定组、批量操作预览，再扩展更复杂策略；衔接原待办 `PCA-IDEA-001`。

包围曝光、焦点堆栈、接片和用户标记的动作序列需要“保持系列完整”选项，避免按重复片规则只留一张。自动识别只给候选标签，无法确定时保留原序列。清晰度不参与拆组；重新分组前展示影响，人工边界继续优先。

**验收。** 特别测 A 像 B、B 像 C、A 不像 C 的链式误合，缺失／乱序时间、跨相机时间偏移、换人不换背景。观察过拆、误合及每 1000 张的人工改组次数，不能只报告聚类平均分。

### 5.4 复核界面与状态表达：P1

**现状。** 已有导航、筛选、逐照片编辑和证据展示。AI 页仍偏向显示单一主状态；人工决定会改变主标签及导出中的复核标记，虽可在详情看到技术信息，日常浏览仍可能把“人工保留”误读为“技术已经通过”。[ai_review_ui.py](../src/ai_cull_assistant/ai_review_ui.py)、[lightroom_results.py](../src/ai_cull_assistant/lightroom_results.py)

**改法。** 使用“人工决定＋技术状态＋摄影表现”并列显示。原因码统一到可筛选类别：读取失败、像素不足、需要选人、需要改框、必要部位缺失、疑似失焦／拖影、证据冲突、AI 失败／过期。用户可先解决主体和数据问题，再处理技术疑难。

照片显示一条最需要行动的原因，详情展示原生局部图、整体位置、来源与版本。提供同主体对应区域的并排比较、同步缩放和清楚的 100% 像素状态；放大显示不能被标成新增真实细节。主页面展示各阶段待办数量和入口，点击导航不发起 API。批量操作要显示范围、数量与影响，并支持恢复。

本轮优先实现第 3.4 节的查看与少量反馈流程，复用现有选片组证据面板和人物编辑入口。无需另建一套强制逐张标注界面；无需先完成持久主体 ID 迁移或整套算法评测才能显示已经保存的证据。

**验收。** 全键盘完成常用路径；200% DPI 下不遮挡主按钮；色觉差异下仍可用文字／图标理解状态。以一批真实照片观察用户能否说清“为什么在这里、下一步做什么”，记录误点和回退次数，不先做整套视觉重设计。

### 5.5 本地摄影表现排序与个性偏好：P2

**改法。** 技术上可用的照片进入独立排序，分别看表情、动作、主体完整性、构图和画面干扰。眨眼、闭眼和表情意图要分开；闭眼动作照可以有较好的摄影表现。全组无技术合格片时，仍可展示“相对较好但技术不合格”，不能隐藏状态。

建立统一排序接口：规则基线、本地模型、远程 AI 都输出分项证据、组内顺序、适用范围与无法判断原因。不同场景使用可解释配置，不默认跨组绝对分数可比。优选需要兼顾多样性，可保留不同动作／构图的代表片及完整系列。

个人偏好学习只使用明确的“这张优于那张”“并列”“都不合适”反馈；身份页的 Y／X／P 不是审美标签。先做小规模成对偏好评估，再尝试轻量重排；提供关闭、重置、导出个人偏好的入口，保持本地存储。

**预期效果与验收。** 目标是减少组内逐张比较时间，降低近似重复片挤占候选的问题。用摄影师盲选的一致性、Top-K 必选片召回、独特动作漏选数和人工用时确认收益。不能以某模型审美分升高代替摄影师评价。衔接 `PCA-OPEN-002` 与 `PCA-IDEA-005`。

### 5.6 AI 调用与任务恢复：P1

**现状。** 已有持久项目状态、结果校验、缓存绑定和 Windows 凭据管理；不是从零实现断点续跑。目前主要是兼容 Chat Completions 的非流式调用，暂停通常等待当前批次结束。[ai_project.py](../src/ai_cull_assistant/ai_project.py)、[ai_api.py](../src/ai_cull_assistant/ai_api.py)、[ai_review_ui.py](../src/ai_cull_assistant/ai_review_ui.py)

**改法。** 提取服务适配器，把传输、图片尺寸／数量限制、结构化结果校验和项目状态分离。按限流、暂时网络错误、无效请求、凭据错误、结果格式错误处理；不要把所有失败都切换模型重发。界面展示当前批次、可暂停边界、失败原因和已完成数量。

沿用已有照片／组指纹与 task／batch ID，补充请求尝试级 attempt／request ID、结果去重和状态未知语义；若服务支持幂等键则利用它。超时可能发生在服务已受理之后，自动重发存在重复费用风险，应保留“状态未知”并提供明确重试入口。主体级技术指纹按第 5.1 节扩展，组内摄影表现指纹仍按实际输入失效。成本预估需要当前服务计费资料，无法可靠估算时只展示请求数与图片量，不伪造金额。

只有用户在复核／选片页主动启动才发送图像；每次结果绑定来源、区域、提示词、模型与服务身份。记录可脱敏导出的错误诊断，禁止日志泄漏 API key 或把完整图片请求体默认落盘。未来本地视觉服务可走同一适配接口，但先测质量、速度和资源占用。

**验收。** 注入网络中断、429、无效 JSON、半批次成功、应用关闭后重开、修改 ROI 后旧响应到达。保证已完成结果不丢、旧响应不覆盖新证据、无用户动作不追加费用。使用桩验协议；真实付费验证单独安排。

### 5.7 工作区、数据迁移与恢复：P0／P1

**现状。** 扫描已有 journal，发布有事务与回滚，源目录换根迁移也已有实现。当前迁移保留相对路径并核对大小／mtime，不支持逐文件改名后自动匹配。不能照搬外部项目后重复搭建第二套持久层，也不能把快速签名当成内容替换和重命名的完整证明。[processing_job.py](../src/ai_cull_assistant/processing_job.py)、[publication_transaction.py](../src/ai_cull_assistant/publication_transaction.py)、[source_relocation.py](../src/ai_cull_assistant/source_relocation.py)

**改法。** 增加只读工作区健康检查：缺失原片、断开的配对、旧证据、未完成任务、孤立缓存、格式版本与可修复建议。为数据格式升级提供显式迁移与副本恢复检查；缓存可重建，人工分组、确认、星级和偏好必须可独立恢复。

逐步建立稳定照片／拍摄 ID，与路径定位分离。大小／mtime 用于快速筛选；未来的文件改名匹配、迁移冲突或疑似内容替换时再补内容指纹，避免每次启动全量哈希。RAW＋JPEG 同一拍摄下各自保留成员身份。当前部分身份／缓存键在 Linux 也做大小写折叠，直接改变会影响旧 AI ID 和指纹；必须先复现历史问题、设计格式版本迁移、碰撞诊断和回滚，再按实际文件系统语义调整。Junction 不递归遍历成重复资产。

把已完成的事务保护扩展为故障注入验收：写入中断、磁盘满、文件占用、进程异常退出、迁移目标重名。可恢复操作提供影响预览和撤销记录；永久删除原片不纳入自动初筛流程。衔接 `PCA-IDEA-002`；历史 Linux 路径问题 `PCA-OPEN-005` 作为回归场景，本轮没有证明它仍可复现。

**验收。** 故障恢复后人工决定、组成员及来源关系与预期一致，不能仅检查 JSON 可以解析。恢复副本不得被默认当成活跃工作区。

### 5.8 Lightroom 衔接：P1

**现状。** 已有路径对应与导入验证，插件能力不能写成尚未接入。缺口是把“已导出文件”与“Lightroom 已成功应用”区分，并补齐真实宿主验收。[lightroom_results.py](../src/ai_cull_assistant/lightroom_results.py)、[ai_project.py](../src/ai_cull_assistant/ai_project.py)

**改法。** 沿用已生成并持久化的 `export_id` 和 `photos` 意图清单；当前插件校验后只取照片数组，应补充根级 `export_id/project_id` 的校验与透传，再增加来源／清单摘要。插件应用后按 `export_id` 产生回执，记录成功、跳过、冲突和失败项，助手据此显示状态。明确回执目录、原子写规则、逐项／分块应用与部分成功语义；重复导入同批次可识别，失败不能显示整批完成。先让回执只读展示，不自动根据回执改变原人工决定。

真实 Catalog 基线验收覆盖 RAW＋JPEG、同名不同目录、虚拟副本、丢失文件、已有星级／关键词、重复导入和写入前取消。目前应用过程没有运行中取消与完整补偿机制；若要提供中途取消，需要先设计可停止边界及部分成功／恢复规则，再做故障验收。对既有字段采用明确的合并／覆盖策略，预览变更范围。保持当前插件方向，不退回人工复制长文本作为主流程。

后续再做人工裁切建议传递（`PCA-IDEA-003`），先解决方向、长宽比、裁切坐标与虚拟副本映射；不把 AI 推荐裁切直接写回原图。`PCA-OPEN-003` 需真实 Lightroom 验收后才可关闭。

### 5.9 性能与资源管理：P1 测量，P2 定向优化

**现状。** 已有自适应扫描资源控制与共享解码，不能简单建议“加多线程”作为新能力。分组在密集候选条件下仍有近似平方级比较；工作区／AI 状态刷新也有全量文件检查成本。[scan_resources.py](../src/ai_cull_assistant/scan_resources.py)、[grouping.py](../src/ai_cull_assistant/grouping.py)、[ai_project.py](../src/ai_cull_assistant/ai_project.py)

**改法。** 分阶段计时：发现文件、元数据、预览、解码、检测、质量、分组、持久化、UI 首屏。用 100／1000／10000 张分层测量，含 RAW＋JPEG、冷启动与热缓存。按真实瓶颈选择缩略图虚拟化／预取、有限候选窗口、增量索引、缓存复用和后台任务预算。

缓存键包含文件成员、内容／快速签名策略、方向、ROI、参数及依赖版本；改评分规则可复用有效原始证据，改解码器则不能盲用旧测量。昂贵模型按需加载，在内存紧张时释放。优化候选筛选必须对照旧结果，检查跨时间窗口的应有组关系是否被截断。

**验收。** 报告首屏等待、扫描照片／秒、阶段 P50／P95、CPU、峰值内存、缓存空间、取消响应及结果一致性。不给未经本机测量的速度承诺，不先上 GPU 或重写语言。衔接 `PCA-IDEA-004`。

### 5.10 工程结构、发布与可维护性：P0／P1

**现状。** 基线约 95 个生产 Python 文件、3.16 万行；测试约 150 个文件、2.88 万行。`app.py`、`ai_review_ui.py`、`processing_job.py`、`crop_dialog.py` 和 `group_editor.py` 各自超过千行。体量不是错误证据，但将 UI、任务生命周期与状态转换混合修改会扩大回归面。

**改法。** 顺序提取状态机／纯计算、存储接口、AI 适配和 UI 控制器，保持外部行为及存量格式兼容。统一原因码、证据版本与参数定义；配置修改记录影响面，避免同一阈值散落在多个界面。重构与改变算法阈值分开提交。

发布清单区分源码、候选包、安装包、现用程序与在线 Release；记录生产树摘要。更新程序按清单替换并保留设置、工作区和 Junction。候选验证通过不自动等于用户接受安装。模型管理显示来源、许可、哈希、大小、加载状态及可选能力，不静默下载模型。建立脱敏诊断导出，帮助定位用户机器上的导入路径、编码和解码差异。

**验收。** 同一生产输入可追踪到构建环境与包清单；在干净 Windows 环境能按步骤重建。在存量工作区副本上回归人工决定与导出一致性。仅文档改动按文档检查交付，不制造无意义的版本更新。

### 5.11 可新增但暂不抢占基础工作的功能：P2／P3

### 6.2 Facet 对本项目最有价值的部分

1. **把分数拆开解释。** 借鉴分项、场景配置和贡献展示，让用户看到某张因表情、构图或技术证据排在前面。技术状态与摄影表现保持独立，直接混合总分不适合本项目。
2. **把绝对质量与组内顺序分开。** 先判技术适用范围，再比较同组表现；全组不合格仍如实说明。连拍优选还要保留独特动作和完整系列。
3. **把个人偏好作为可关闭的重排层。** 它改变推荐顺序，不重写客观测量，不覆盖用户决定，不把未确认的人脸自动收为参考。
4. **分阶段处理、缓存与恢复。** 当前项目已经有对应基础，借鉴重点应是任务粒度、输入版本和失败可见性，避免重复建立第二个任务系统。

建议借鉴顺序：分项结果结构 → 组内排序对照 → 原因界面 → 明确偏好反馈 → 小规模本地重排。直接移植 Facet 的所有评分项、权重和模型，会把其场景假设与误差一起带入。

### 6.3 每次引入外部做法的准入记录

每个候选保存一张简表：要解决的现有失败类型、固定源码提交、代码／模型／数据许可、输入尺度与预处理、输出含义、与当前基线的差别、CPU／内存／包体成本、对照结果、启用方式和退回条件。没有改善目标错误，或收益只覆盖少量难例时，分别选择不接入或仅难例调用，不因功能数量增加就默认加入生产。

## 7. 评测与准入

### 7.1 建立六类基线，不只测清晰度

| 方向 | 必须观察的错误／成本 | 需要的真值或验收材料 |
| --- | --- | --- |
| 技术质量 | 糊片误保留、清晰片误弃置、待确认率、各原因占比 | 明确主体、必要区域、可见性、来源充分性和技术标签 |
| 主体与身份 | 认错人、漏人、未知人被误接纳、多参考污染 | 人工确认身份、困难负例、区域归属与未知类别 |
| 分组 | 误合、过拆、链式混组、人工修正次数 | 拍摄意图与允许的组边界；不假定只有一种唯一正确分组 |
| 摄影表现 | 必选片漏选、偏好反序、重复候选挤占、多样性丢失 | 摄影师成对选择，允许并列与都不合适；组内必选清单 |
| 产品流程 | 人工分钟数、重复操作、恢复后差异、AI 重复调用 | 真实工作流观察、操作记录、故障恢复快照 |
| 交付与平台 | 路径错配、星级／关键词误覆盖、包与源码不一致 | Windows 候选清单、真实 LR 回执、存量工作区副本 |

先整理现行方案的真实失败，用错误类型决定实验。近期入口为用户漫展照片的扫描结果与纠错反馈，见第 3.4 节。合成演示只验证工具操作，公开诊断样本及临时 AI 标签只作为诊断材料；不能写为人工真值、独立测试集或生产准确率。上表中的技术真值要求用于算法准确率评测，不用于限制日常扫描、查看和问题反馈。

### 7.2 样本、许可与数据划分

本节用于后续专项评测。普通用户无需逐张准备这些表单；本地来源与运行信息尽量自动记录，技术标签只对已安排的评测子集采集。经结果提示产生的用户反馈保留为开发材料；独立评价需明确标签来源与数据划分。

- 建立样本清单：合法来源／用途、原文件哈希、拍摄组、人物、RAW＋JPEG 关联、相机镜头、ISO、方向与图像尺寸。只记录评测所需的个人信息；私人样本默认本机处理。
- 技术标注拆到左右眼、脸核心、身体必要部位和风景主体／纹理区域。每项可标不可见、像素不足、无法判断，记录分歧及复核结果。严重程度与“是否应该交付”分开，艺术性运动模糊可由用户决定保留。
- 关键样本尽量由多名标注者独立判断，记录成对一致率；样本量和标签形式适用时补一致性统计。只有本人标注的启动集如实标明，不能冒称专家共识；主观偏好分歧也不应全部强行裁成唯一答案。
- 同一快门的 RAW 与 JPEG 作为一个统计单元。固定 RAW 解码器、色彩／锐化配置、方向、裁切与缩放，报告不同来源的状态一致率、组内排序翻转及原因。两种处理结果可以有合理差异，不以强迫一致作为通过条件。
- 同一人物／拍摄场次／连拍／近重复及对应 RAW＋JPEG 不跨调参与封存测试。人脸识别评测允许测试身份内部设置参考图与查询图，但阈值选择用不同身份／拍摄组，避免拿测试查询调参数。
- 同时建立“固定人工 ROI 的算法测试”和“从原图自动定位到建议的端到端测试”。只评价检测成功照片会掩盖漏检，端到端分母必须包含失败与待确认项。
- 可先用 100～300 张分层样本定位流程问题，再按错误率目标和困难类别扩充。这个范围是启动建议，不是证明极低错误率所需的充分样本量。
- 封存集不参与反复调参；每轮查看失败后的改进使用开发集，正式比较按预先约定执行。版本变化记录进入样本清单，避免测试集逐渐成为训练集。

### 7.3 指标必须能揭示“全都待确认”的问题

技术质量至少同时报告：

```text
清晰片误弃置率 = 真值清晰且建议弃置的数量 / 真值清晰数量
糊片误保留率   = 真值不可用且建议保留的数量 / 真值不可用数量
自动决定覆盖率 = 自动保留或弃置的数量 / 全部待评照片数量
待确认率       = 待确认数量 / 全部待评照片数量
```

另报“建议保留中实际不可用的比例”和“建议弃置中实际可用的比例”，明确分母与样本分布。真值无法判断的样本单列，不能随意塞入清晰或模糊；它们仍参与流程负担统计。

建立“看似清楚但主体不可用”的压力子集：背景锐而脸虚、单眼虚、锐化光晕、强降噪、JPEG 边缘伪影、眼镜反光。另列唯一可用片、关键人物片和用户必选片的误弃建议，避免这些高损失错误被大量普通照片平均掉。“弃置”仍是建议标记，不是自动删除原片。

在相同覆盖率比较错误风险，同时画出覆盖率与错误风险的关系。各关键场景单列数量、错误数和置信范围；照片有组内相关性时按拍摄组进行统计或重采样。少量样本零错误不证明真实错误率为零。

身份报告误接纳、误拒绝、未知拒识和确认覆盖率；分组报告配对关系及过拆／误合，并补人工改组次数；排序报告成对偏好、Top-K 必选召回与独特动作漏选。总体单一分数不替代这些指标。

准入门槛应在看封存结果前设定：最不能接受哪种错误、可接受多少人工复核、目标机器允许多少耗时。此文不伪造“准确率 99%”或固定提速承诺。

### 7.4 模块比较与实验顺序

1. 固定原图取样、坐标和人工 ROI，复现当前基线，保存每张／每区域结果。
2. 做一个低成本改善：左右眼独立证据与可见性；先查其收益和新错误。
3. 在同一输入上加入一种局部模糊候选，观察是否补足现有失败；低纹理误判单列。
4. 加一种噪声影响候选，检查高 ISO 糊片误保留是否减少，同时观察睫毛、发丝与布料细节是否被误抹。
5. 用 PyIQA 等固定工具评测 2～3 个合适学习型候选。记录模型、权重、精度、输入块、设备、加载与推理时间；原始 LIQE 与不同封装实现分别标识。
6. 做消融：基线、单模块、合理组合逐项比较。只有难例收益时采用条件调用；没有稳定收益就保留研究结果并停止集成。
7. 对最终候选做端到端封存测试、Windows CPU 和包体检查，再以仅记录建议的影子模式运行；之后才考虑可选开关与默认策略。

原生局部 ROI 过小或不满足模型预训练尺度时需要单独验证；插值放大不能恢复缺失细节。不要通过反复调阈值把检测失败伪装成算法问题解决。

### 7.5 性能、兼容与发布验证

分别报告冷启动模型加载、首次扫描、热缓存重开、修改一个 ROI 后局部重算。记录设备、CPU 线程、内存、依赖版本、输入规模与缓存状态；不能把开发机 GPU 数字写为本机 CPU 体验。

模型对照在目标 Windows CPU 上固定 batch 与线程配置；可先采用 batch=1 基线，另测批处理收益。冷态用新进程的模型加载与首图，暖态注明实际预热方式。分开记录解码、检测、评分、组内排序的 P50／P95、吞吐和峰值内存口径。产品人工用时采用同批次顺序平衡或随机安排的对照，记录总用时、复核数量、点击数、纠正误弃次数及用户偏好，降低熟悉照片后的练习效应。

工程测试覆盖纯逻辑、状态契约、故障注入和少量完整工作流。只为影响行为的改动增加相称测试，不为每个界面文案写镜像测试。算法样本评测、真实 LR、真实付费 AI 与 Windows 打包各自单列，不能相互替代。

每次候选交付附一页结果：基线／提交、改变了什么、适用样本、主要收益、新增错误、未验证项、资源成本、默认开关和回退方法。旧人工记录不因策略更新批量改写；需要重算时由用户明确启动。

## 8. 迭代顺序与任务拆分

### 8.1 推荐实施顺序

| 阶段 | 要交付的具体结果 | 完成标准 | 可获得的效果 |
| --- | --- | --- | --- |
| **G0：确认基线与跨机契约** | build18 用户验收清单；共同 Git 基线；共享开发契约；handoff 格式；环境诊断 | Windows／Linux 能确认同一祖先；一项小功能可完整往返，原片与现用包无意外改动 | 下一轮接续由逐文件考古变为有限差异审查 |

| **G3：技术质量竞争实验** | 逐眼基线；固定 ROI 对照；模糊／噪声／学习型候选消融 | 封存集在约定覆盖率／风险与 CPU 预算下通过；未通过不启用 | 有证据地减少特定误判，保留退回基线的能力 |

### 8.2 接下来最合适的三项任务

**任务 A：把开发接续做顺（源码往返已完成，继续沿用）。** 使用共同 Git 历史、共享开发契约、环境检查与 handoff 验包流程接续。推送仍按当次授权；增量 bundle 作为备用。任务 A 的完成不代表后续工具已打包进现用 EXE。

**任务 B：程序先判断，用户按结果纠错（下一项）。**

- B1：核对现用包与候选源码，复用已有扫描、原因与框选功能。在独立工作区准备逐图结果查看入口：全量状态、实际主体与已记录区域、原生局部、来源和简短理由；缺失证据明确列出。只读报告可作为先行交付，但不另建第二套评分器。
- B2：增加少量反馈记录，支持文字指出错误、选主体／关注区域和明确的人工留弃；保存原建议与反馈。普通照片无需操作，反馈默认不触发重算、改组、上传或训练。
- B3：用户指定本地输入与批次后，用同一明确版本的原算法跑真实漫展流程。窗口内查看全部结果，优先看弃置和待确认，也能抽看保留片。明确应用改框时才重测并对照；未支持的区域显示能力缺口。若未来需要区域级重算，再独立处理稳定 ID 与细粒度失效。

验收以实际工作流为准：读图／缩放不重扫；未记录的指标或区域不伪造；一条反馈可定位原图与原扫描；关闭重开仍保留；改框只使相关旧技术证据失效；人工决定、原片和人工组保持。首轮不改评分、阈值、采样或主体选择规则，不新增质量模型，不替换现用程序。

**任务 C：围绕已发现问题做专项评测（后续）。** 从 B 的反馈分类中选择要解决的问题，只为相关案例补必要区域技术标签，冻结基线与输入，再选择逐眼、模糊、噪声或质量模型中的适用候选。公开样本可补困难类型，用户无需替整批照片手工作答。开发案例与独立封存评价分开；报告新增错误、待确认和 CPU 成本后再决定算法投入。

当前顺序为沿用 A → 完成 B 的真实扫描查看／反馈 → 按问题安排 C。无需等 28 张样本全部标注，才允许使用程序或查看原因。真实 Lightroom 和存量工作区恢复验收独立补齐，不作为本轮 B1 的附加大改造。

#### 8.2.1 按可用产品交付，尽快落实原有设想

项目目标仍是批量初筛、主体修正、同组比较、摄影表现选片和 Lightroom 接续。近期不能把完成更多登记表、合成演示或测试数量当作产品进展，也不能让所有日常功能等待算法研究结束。以下轮次是交付顺序，不是已经启动或完成的功能；工期应在各轮核对实际缺口后给出。
